# Odoo label source (#90) — invariants and gotchas

- **Contract** (#90 comment of stream david4, 2026-09-28): `POST /food/print/next|ack|heartbeat`, JSON-RPC 2.0 envelope, `Authorization: Bearer <key>`. BOTH error kinds come with HTTP 200: a top-level `error` (auth/exception) first, then `result.error` (business). Empty queue = `{"lines": []}`. Odoo sends `false` for empty fields (text AND ids). `/next` has NO lease: it re-offers a line until acked.
- **Print-once invariant (ledger `sent`):** a `line_id` whose bytes reached the spooler is NEVER printed again, whatever Odoo sends — its stored result is re-acked. To reprint, Odoo must issue a NEW line. Only a line rejected BEFORE any send (`empty png`, `size`, `invalid line: …`) is processed anew once Odoo stored that verdict. Do not add a "re-queued → print again" path without a per-cycle token from Odoo (re-review 🔴: an Odoo state bug would reprint every second).
- **Ack failures:** a transport error fails the poll (backoff ≤ 60 s); a JSON-RPC/protocol error on ONE line keeps only that ack owed (`AcksOwed`) — it must never block `/next` or other lines. A timed-out batch is acked `outcome unknown … check the printer before reprinting`, never "failed".
- **TSPL** mirrors the captured BarTender bytes: `SIZE 72.7 mm, 110.1 mm` (with the space), CRLF, `BITMAP` 1-bit = WHITE, no GAP/DENSITY/SPEED. Label dots = `round(mm × dpi / 25.4)` (floor would reject Odoo's 880-px height). Fixture: `src/odoo_source/fixtures/bartender_bitmap_7x80.bin`.
- **The roll is per batch (#108, `label_size.rs`).** The 50 × 30 mm crate QR labels print on the SAME TSC as the 72.7 × 110.1 mm bakery labels; the store swaps the roll, and Odoo's roll interlock prints one roll at a time.
  - A `/next` batch may carry `label_width_mm` / `label_height_mm` (+ optional `dpi`) at BATCH level. That roll drives `SIZE`, the PNG size check, the centring, the job history `paper_size` and the heartbeat `paper_size` (= `SIZE` of the last batch document printed or tried — recorded once its lines are `sending` — the config roll before the first).
  - No size = the `[client.odoo]` roll, byte-identical to before #108. "No size" is absent / `false` / `null` / `0`: an unset Odoo `fields.Float` reads `0.0`, so a format with no size must never refuse the bakery batches. Rotation / offsets always come from `[client.odoo]`.
  - The size is the PAIR. One alone, `dpi` without the pair, a non-number, width outside 10–108 mm (ML241P head), height outside 10–300 mm, or dpi ∉ {203, 300} → every printable line is acked `size: <reason>`, nothing is sent. The line is processed anew when Odoo re-offers it (rejected before send).
  - A bad value never fails the `/next` poll: `rpc::BatchNumber::NotANumber`, not a parse error — a parse error would block the batch with no visible ack.
  - Logged per batch: `label size 50x30 mm (source: batch|config)`; a WARN `roll changed <old> -> <new>` when a document goes out on another roll than the previous one.
  - **Operational:** after a roll swap the TSC needs a label-gap calibration (the printer keeps its stored calibration; devbridge sends no GAP).
  - The BarTender safe-margin WARNs are measured on 581 × 880 dots, so they apply only on that canvas (`layout::BARTENDER_CANVAS`). The offset-crop WARN applies on every roll.
- **Orientation = the golden BarTender job (#95).** Rendered in printer coordinates, the known-good BarTender job `fixtures/bartender_label_468e3256.tspl` is the readable label ROTATED 180° with the same `DIRECTION 0,0` header — so `layout::place_label` rotates the bitmap itself (rows AND dots reversed, padding stays right/white) and centres it (`BITMAP 2,0` for 576 × 879). Never "fix" orientation with `DIRECTION 1` (untested firmware semantics) or by asking Odoo for a pre-rotated PNG (printer language stays in devbridge). Offsets are in READING orientation. Any layout change is proven by the test-only renderer in `tspl_golden.rs` (dot-for-dot vs the BarTender render, real Odoo label 4 fixture) — no store test prints.
- **The renderer convention:** `render(doc).rotated_180()` = the label as read. Measured: reference canvas 581 × 880, printer ink (29,17)-(558,833), as read (23,47)-(552,863); label 4 as read (26,29)-(549,752), document 63 406 B. The measured reference is BITMAPs + BARs only: the job's firmware EAN13 (`BARCODE 511,120,"EAN13",67,1,180,…` — rotation 180, the same convention) is RECORDED in `Printed::not_drawn`, not drawn (the #95 Python prototype skipped it silently and a first renderer rejected it — every golden test panicked). The renderer errors on any other unknown drawing command or `DIRECTION` ≠ 0,0 — extend it (with a test) rather than letting a command pass silently.
- **api_key** only in the `Authorization` header and `config.toml` (redacting `Debug`, never on an installer command line — post-install reads `$env:DEVBRIDGE_ODOO_API_KEY`).
- Integration tests use a fake Odoo (axum) + a fake spooler `PrintBackend`: `tests/odoo_source/` is ONE multi-file target (`fake.rs` = fakes + `Rig`, `batches.rs`, `label_size.rs`; split at 1075 lines). The real spooler path is E2E step 35 on the RAW E2E client (fake Odoo on pz-server :9230). Step 35 also requires the heartbeat's `paper_status`/`error_status` ≠ `unknown` (#97). Since #108 it also prints a 2nd batch on the 50 × 30 roll (EventID 307 == its TSPL size) and requires the heartbeat `paper_size` = `50x30 mm`.
- **Heartbeat printer status = native winspool, never a spawned process (#97).** `printer_status.rs` reads `OpenPrinterW` → `GetPrinterW(2)` → `PRINTER_INFO_2W.Status/Attributes` (3–26 ms) in `platform_windows.rs`, via the shared `crate::winspool::PrinterHandle`. The old per-heartbeat `powershell Get-Printer` cold-started 2.6 s+ and timed out 447× on spisska-pc → `unknown`. Value contract: the PowerShell `PrinterStatus` enum IS the `PRINTER_STATUS_*` bitmask, so `STATUS_NAMES` are its members snake-cased (`IoActive` → `io_active`), ascending bit order; `PRINTER_ATTRIBUTE_WORK_OFFLINE` → `offline`; unknown bits → `status_0x<hex>`. `PRINTER_INFO_2W` needs the `Win32_Security` feature of windows-sys (besides Gdi + Printing).
- **`PrinterStatusReader` guards a hung spooler**: 5 s guard (`unknown`), at most ONE blocking read in flight (`StillRunning`), and logs by state (`Seen`): WARN on a new failure (TimedOut and StillRunning are the SAME hung failure), INFO "printer status changed" on the first status / a change / recovery, quiet otherwise — never a line every 30 s. The Win32 query is the injectable `QueryFn`, so the guard and the log decision are unit-tested on Linux.
