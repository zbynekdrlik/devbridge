# E2E suite (devbridge-e2e + deploy/e2e-*.ps1) — gotchas

- **The CI E2E is an ISOLATED instance**, never the production one: data dir `C:\ProgramData\DevBridge-E2E`, gRPC 50152, dashboard 9220, `client_id = "e2e-client"`, task `DevBridgeE2E`. The setup rewrites its `config.toml` fresh every run. Never point an E2E step at `C:\ProgramData\DevBridge` (pz-snv is the live pjsnvs store POS).
- **To exercise a real installer function in E2E** (post-install helpers live in `installer/DevBridgeInstallerLib.ps1`, install.ps1's inline), dot-source `deploy/lib/Get-FunctionSourceFromScript.ps1` and extract it by AST — exactly like the Pester suites and the #70 serial-bridge merge in `e2e-setup-client-local.ps1`. Never run post-install/install for real in E2E: it hard-codes the production data dir. TWO sanctioned runs, both on pz-snv in `e2e-deploy-client`, both hashing the production `config.toml` before/after: `post-install.ps1 -ValidateOnly` (read-only) in the packaging gate (#80), and `deploy/e2e-real-install-upgrade.ps1` (#93, the job's FIRST step) — the checkout's real `install.ps1` with `DEVBRIDGE_INSTALLER_PATH` = the CI build, run as SYSTEM under 5.1 while trays run in the logged-on user's session (started via a temp Interactive task if missing) AND in session 0, i.e. a full real upgrade of pjsnvs (tray + service stop, NSIS, post-install with the config preserved). It FAILS when nobody is logged on to pz-snv (the incident needs a user-session tray) -- log the `pz` user back on after an unattended reboot. Trays are identified by PID + StartTime. Its finally-block restores config.toml from a byte copy if it changed and starts `DevBridgeService` again, each cleanup in its own try.
- **`src/main.rs` is ~2440 lines.** Put a new step in its own module (e.g. `src/serial_bridge.rs`: pure validators + unit tests, plus the async step) and only wire it in `main`. Renumber every `[N/total]` print and the final `All N E2E tests passed` line. The server-driven retry test (#56) must stay LAST (it points the client at a bad printer).
- **A step that waits for a client retry loop must wait longer than the loop's backoff cap.** By the time late steps run the client has been up for minutes, so any backoff (e.g. the serial reader's 30 s cap) is already maxed.
- **Formatting the workspace-excluded e2e crate from a nested worktree:** `cargo fmt --manifest-path crates/devbridge-e2e/Cargo.toml` fails ("believes it's in a workspace" — it resolves the parent checkout's Cargo.toml). Use `rustfmt --edition 2024 crates/devbridge-e2e/src/main.rs` (formats its modules too).
- **Quoting E2E evidence from CI:** `gh run view <id> --log` can prefix lines with the wrong job name (the E2E Test output also shows up under "Test"). For a specific job use `gh api repos/zbynekdrlik/devbridge/actions/jobs/<job-id>/logs`.
- **There are TWO isolated E2E clients on pz-snv since #88:** `e2e-client` (PDF, `DevBridge-NullPrinter`) and `e2e-raw-client` (`windows_spooler_raw`, data dir `DevBridge-E2E-Raw`, dashboard 9222, task `DevBridgeE2ERaw`, target `DevBridge-E2E-Raw` = Generic / Text Only on `NUL:`). `e2e-wait-ready.ps1` leaves the RAW one PENDING; step 34 (`src/raw_passthrough.rs`) approves it, prints, and REJECTS it on every path. Any step that picks "a client" must select `e2e-client` by machine_id, never `.first()`. Expected `connected_clients` = 2.
- **Step 35 (`src/odoo_source.rs`, #90): the E2E binary itself listens** (fake Odoo, pz-server TCP 9230). pz-server's firewall blocks inbound except the service binary, so `e2e-setup-server.ps1` adds `DevBridge-E2E-FakeOdoo` (remote 10.78.2.10 only) and `e2e-cleanup.ps1` removes it. The RAW client's `[client.odoo]` comes from the real installer functions; the setup deletes `odoo-ledger.db*` each run (a leftover ledger would re-ack instead of print). Line ids are time-based so runs never collide.
- **NSIS silent install exits 2 when a tray app `devbridge-app.exe` still runs** (any user session; pz-server has ~20, one per RDP user). The fix lives in `install.ps1` (`Stop-DevBridgeTrayApps` before NSIS, #93); both E2E setup scripts AST-extract and call THAT function — never hand-copy installer logic into a harness (the 19c51fe copy kept CI green while 6 stores broke). A plain removal is not possible: the harnesses run NSIS directly. If NSIS still fails they restart the PRODUCTION `DevBridgeService` before throwing; after any red E2E deploy step, check `http://10.78.2.10:9120/api/status` and `http://10.88.1.100:9120/api/status` anyway.
