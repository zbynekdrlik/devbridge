# Odoo device jobs / pokladňa (#99) — invariants and gotchas

- **Contract**: odoo-erp `addons/company_pokladna_api/docs/device_job_api.md` (develop). `POST /pokladna/bridge/next|ack|pending|heartbeat`, JSON-RPC 2.0, Bearer key of scope `pokladna_bridge` (a DIFFERENT user + key than the label printer's). Success = `result.ok == true`; a business refusal is `result = {"ok": false, "error": {"code", "message"}}` → `RpcError::Refused{code}` via `odoo_rpc::require_ok`. A top-level JSON-RPC `error` (auth) is `RpcError::Rpc`. The label contract's `result.error` TEXT stays `RpcError::Business` — both go through the ONE shared `odoo_rpc::OdooTransport` (never copy the transport).
- **Exactly once = the journal** (`device-journal.db`, WAL + `synchronous=FULL`): `received` is committed BEFORE any device contact; only the caller whose `received → executing` UPDATE changed a row may call `execute`. A job id already in the journal is NEVER executed again (Odoo handing it out twice only re-sends its stored outcome). On restart every `received`/`executing` row becomes `indeterminate` and is reconciled THROUGH ITS DEVICE (`DeviceExecutor::reconcile`) — first, before any `indeterminate` ack is owed. The first final outcome wins (`record_outcome` refuses to change `done`/`failed`).
- **One control loop owns `pending` + `next`** (`device_jobs::control_loop`) — never concurrent. `pending` at start, after ANY failed `next` (the response, and a claimed job with it, may be lost) and after a `too_early`; no `next` before a `pending` round succeeded. `not_received` is acked ONLY there and ONLY for a job the journal does not know. `next` HTTP timeout = `wait_s + 10 s` (`Timing::next_timeout_margin`); `wait_s: 0` (no Odoo waiting slot) → sleep 1–2 s; an empty reply faster than `min_long_poll` is treated the same (never spin).
- **Never ack `failed` unless nothing ran.** Executor errors / timeouts / panics are `indeterminate`. The bridge's `execute_guard` (240 s, below Odoo's 300 s claim timeout) reports `indeterminate` early but the device's serial queue WAITS for the real answer (which becomes the late ack) — a device is never driven by two jobs at once. Every device has its own serial worker (a PIN wait never blocks a receipt, a slow till never blocks another).
- **Refused without device contact** (validated BEFORE journaling and inserted directly as `failed` with `Journal::insert_refused` — one write, so a crash can never make it look in flight; acked `failed`, text says "nothing ran"): `card.purchase` with `amount` not a finite number > 0 → `bad_amount`; a type without a registered executor (`fiscal.*` → fiscal, `card.*` → card, anything else) → `unsupported`. Since #100 an enabled `[client.pokladna]` (without `test_executor`) sends every `fiscal.*` job to the till's Portos; `card.*` stays `unsupported` until TIM (#102) — no store gets `[client.pokladna]` before the owner approves the pilot.
- **Acks** are journaled and re-sent by the acker task until Odoo accepts them: transport error → stop the round + backoff; JSON-RPC / protocol error on ONE ack → keep only it owed, continue; a refusal (`not_found`, `not_claimed_by_you`, …) is final (`ack_note = "refused: …"`, ERROR log). `duplicate` = accepted. Every journaled outcome calls `Shared::outcome_recorded()` (wakes the acker, the LAN reporter and every waiting LAN API call — #101); `ack_soon()` alone only where an ack is owed again without a new outcome — the idle tick is only a safety net (the integration tests set it to 30 s on purpose so a missing wake-up fails them).
- **LAN API of the tills (#101)**: LAN jobs share this whole path (journal table `lan_jobs`, NEGATIVE job ids, same executors / queues / reconciler) — invariants in `.claude/rules/lan-api.md`, contract in `docs/lan-api.md`.
- **Logging**: job id / type / kasa / client_uuid / sale name / state changes; of the payload ONLY `amount` + `currency` (`DeviceJob::money`, its `Debug` prints payload KEYS only); never the api_key. Error texts never quote a response: `BridgeApi` sets `BodyExcerpt::SizeOnly` on the shared transport (a truncated `next` body would otherwise put card data into a WARN line) and parse errors name the SHAPE (`odoo_rpc::value_shape`: keys / type), never values.
- **Ack hygiene**: `error` loses NUL characters and is cut to 2000 chars; an executor's `Failed` code is forced into `[a-z0-9_.-]{1,64}` and the channel codes `indeterminate` / `not_received` become `device_<code>` (a device failure must never read as "unknown" / "never received"). `prune` (400 days) keeps rows whose ack Odoo REFUSED — Odoo may still list them in `pending`.
- **Device queues (#100)**: one serial worker per `DeviceQueue` = (kind, device address) — `DeviceExecutor::endpoints()` lists every address (one Portos per till), `endpoint(job)` routes a job; the default (test executor, a future single-device adapter) is one queue per kind. A job waiting in its queue longer than `Timing::max_queue_wait` (120 s) is refused `expired_local` via `Journal::fail_unstarted` (only a still-`received` row). `DeviceExecutor::check` refuses a job BEFORE journaling (Portos: `bad_payload` / `no_kasa` / `bad_client_uuid`); `status()` must not block — `refresh_status()` probes on `Timing::status_refresh` (15 s). TIM (#102) plugs in the same way (`terminal_ip` per till).
- **Portos executor (#100, `device_jobs/portos/`, contract `docs/device-jobs-fiscal.md`)**: externalId = `"dbj-"` + first 32 hex of SHA-256(`"<kasa_id>:<client_uuid>"`) (36 chars; `payload::external_id`, test vectors in the contract doc §2 — #101 must compute the same), lookup (`GET /api/v1/requests/receipts/receipt?CashRegisterCode=&ExternalId=` — CashRegisterCode is REQUIRED, taken from `data.cashRegisterCode`) BEFORE every register POST; `Journal::mark_device_contact` (column `device_contact_at`, committed BEFORE the POST; a #99 journal is migrated and its in-flight rows marked "contact unknown") is what makes reconcile's `not_executed` provable (not found + never contacted) — the proof lives in the journal, never in a second file. `failed` ("nothing ran") only for: `bad_payload` / `no_kasa` / `bad_client_uuid` (before journaling), `expired_local`, lookup `portos_unreachable` / `portos_lookup_failed` and `bridge_error` (nothing posted), connect refused (`Reply::Unreachable` = reqwest `is_connect()`, pooling OFF so a dead pooled connection never reads as "sent"), HTTP 400/422 code −900, 401, 404/405 without a Portos code. A lookup/reconcile receipt must NAME our externalId (a null one is accepted only on our own POST's answer); lookup "not found" = 204, a 4xx with code −104, or a 404 PROBLEM body (a real 7.0.4 answers a miss with a 404 `ProblemDetails` WITHOUT a code) — a bare 404 is `portos_lookup_failed`. Portos refuses an ExternalId over **40 characters** (`NineDigit.eKasa.ID`, HTTP 400 −900 on the lookup) — why the key is hashed (a readable `dbj-<kasa>-<36-char uuid>` was 42+). Portos checks `roundingAmount` within ±0.04. A real 7.0.4 with the InMemory PDF printer answers `open_drawer` 200 `opened: false`, a copy of an unknown receipt 403 −104. A 5xx is NEVER "nothing ran": −502 PrintReceiptError comes AFTER registration. Not found + sent stays unknown (Portos docs don't prove a lost request was never stored). Drawer / copy: unknown → `outcome_unknown_retry_safe` (the one documented exception). Portos 9 removed Deposit / Withdraw / Invalid; the pilot runs 7.0.4. NEVER send anything to a store's Portos.
- **Real-Portos CI (`portos-live` job, `deploy/ci-portos-inmemory.ps1`)**: pinned 7.0.4 MSI (vendor URL `…/apps/portos-ekasa-api/portos-ekasa-api-win-x64-v<ver>.msi` + SHA256 — the old `…setup.latest.msi` redirects to the download PAGE), `msiexec /qn`, `PUT /api/v1/settings` InMemory + Playground, service restart (InMemory is wiped on restart), identity from `GET /api/v1/identities` → `DEVBRIDGE_PORTOS_CASH_REGISTER_CODE`. Tests behind `--features portos-live` (`tests/device_jobs/portos_live.rs`, `--test-threads=1`, the step asserts the exact passed count); a lost answer = a TCP proxy that forwards the POST and drops/holds Portos' answer; receipts are counted with `GET …/next_number`. The InMemory test identity expires **15.11.2026** (the setup warns 30 days ahead) and a newer MSI does NOT fix it: every MSI the vendor offers (7.0.4, 7.2.2, 8.0.1, 9.0.6) bundles the SAME identity — a base64 PKCS#12 inside `NineDigit.eKasa.API.dll` of the .NET single-file bundle, sha256 `660a119e1ecfc5a34b9566917246526a2c46a269e801559428282c980400c423`, cash register `88812345678900001`. Only a renewed identity from NineDigit helps (a new release, or a keystore: GitHub secret, loaded by the setup via `POST /api/v1/certificates` + `POST /api/v1/identities`, both in 7.0.4) — evidence #101 comment 6197650284.
- **`fiscal.paragon` (#115, contract §3.6)**: `ReceiptKind::Paragon` → `POST /api/v1/requests/receipts/paragon` on the same `register()` path (lookup before POST, same queue, same reconcile). A sale's data keys plus REQUIRED `issueDate` (RFC 3339 with its offset, never later than this PC's clock — `check_payload_at` / `issue_date_problem` take `now` so the equal case is tested) and `paragonNumber` (1 ..= 4 294 967 295 — the 7.0.4 swagger says `int32`, Swashbuckle renders a C# `uint` the same way; Portos answers what it cannot take with 400 → `portos_validation`). `customer` and any top-level `print` are refused (Portos prints a paragón on paper). The result adds `paragon_number` (only on a paragón). The 7.0.4 swagger can be read from the pjsnvs PC with a GET of `http://localhost:3010/swagger/v1/swagger.json` (MCP `win-pjsnvs-pokladna`; `Invoke-RestMethod` returns 0 paths in PS 5.1 — read `(Invoke-WebRequest …).Content` and cut around the path / schema name).
- **Odoo's golden documents (#110)**: `src/device_jobs/portos/testdata/odoo/` holds the receipts Odoo composes, byte-for-byte from odoo-erp (source commits + sha256 + refresh command in its README); the unit parity tests run them through the real checker and `portos_live.rs` registers them. Never edit them by hand; a refresh is a reviewed contract change. A commit message must not write `#9243`-style odoo-erp numbers (the design gate reads them as THIS repo's issues) — write "odoo-erp issue 9243".
- **Mutation gate**: logging-only `if` branches become missed mutants — log one line with the value as a field (e.g. `recorded`, `reopened`), no arithmetic in log fields (`attempts + 1` was a missed mutant); `JournalEntry::owed_ack` guards and the journal timestamps are tested on the entry itself (the SQL already filters them).
- **The `test` executor** (`test_executor = true`, E2E ONLY, never written by the installer) drives no device: a job needs `payload.devbridge_test.outcome` = `done` (+`delay_ms`) / `failed` / `indeterminate` / `crash`; anything else is refused "nothing ran". Its durable `test-device.db` is the device's memory reconcile reads. `crash` records the run and EXITS THE PROCESS (code 75) — tests inject a returning `CrashHook`.
- **E2E step 36** (`crates/devbridge-e2e/src/device_jobs.rs`): fake Odoo on pz-server TCP **9231** (the `DevBridge-E2E-FakeOdoo` firewall rule carries 9230 + 9231), `[client.pokladna]` on the RAW E2E client from the REAL installer functions (`wait_s` 10, asserted on every `next`) + `test_executor = true`. The forced restart is a real process death: the RAW task has a 1-minute keep-alive trigger (`-Once -RepetitionInterval 1 min`, `MultipleInstances IgnoreNew`, verified on pz-snv PS 5.1) — `e2e-cleanup.ps1` unregisters the task. The setup deletes `device-journal.db*` / `test-device.db*` of the E2E data dir each run (job ids are time-based too).
