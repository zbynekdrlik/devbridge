# Odoo device jobs / pokladňa (#99) — invariants and gotchas

- **Contract**: odoo-erp `addons/company_pokladna_api/docs/device_job_api.md` (develop). `POST /pokladna/bridge/next|ack|pending|heartbeat`, JSON-RPC 2.0, Bearer key of scope `pokladna_bridge` (a DIFFERENT user + key than the label printer's). Success = `result.ok == true`; a business refusal is `result = {"ok": false, "error": {"code", "message"}}` → `RpcError::Refused{code}` via `odoo_rpc::require_ok`. A top-level JSON-RPC `error` (auth) is `RpcError::Rpc`. The label contract's `result.error` TEXT stays `RpcError::Business` — both go through the ONE shared `odoo_rpc::OdooTransport` (never copy the transport).
- **Exactly once = the journal** (`device-journal.db`, WAL + `synchronous=FULL`): `received` is committed BEFORE any device contact; only the caller whose `received → executing` UPDATE changed a row may call `execute`. A job id already in the journal is NEVER executed again (Odoo handing it out twice only re-sends its stored outcome). On restart every `received`/`executing` row becomes `indeterminate` and is reconciled THROUGH ITS DEVICE (`DeviceExecutor::reconcile`) — first, before any `indeterminate` ack is owed. The first final outcome wins (`record_outcome` refuses to change `done`/`failed`).
- **One control loop owns `pending` + `next`** (`device_jobs::control_loop`) — never concurrent. `pending` at start, after ANY failed `next` (the response, and a claimed job with it, may be lost) and after a `too_early`; no `next` before a `pending` round succeeded. `not_received` is acked ONLY there and ONLY for a job the journal does not know. `next` HTTP timeout = `wait_s + 10 s` (`Timing::next_timeout_margin`); `wait_s: 0` (no Odoo waiting slot) → sleep 1–2 s; an empty reply faster than `min_long_poll` is treated the same (never spin).
- **Never ack `failed` unless nothing ran.** Executor errors / timeouts / panics are `indeterminate`. The bridge's `execute_guard` (240 s, below Odoo's 300 s claim timeout) reports `indeterminate` early but the device's serial queue WAITS for the real answer (which becomes the late ack) — a device is never driven by two jobs at once. Fiscal and card have separate serial workers (a PIN wait never blocks a receipt).
- **Refused without device contact** (acked `failed`, text says "nothing ran"): `card.purchase` with `amount` not a finite number > 0 → `bad_amount`; a type without a registered executor (`fiscal.*` → fiscal, `card.*` → card, anything else) → `unsupported`. So until Portos (#100) / TIM (#102) exist, an enabled `[client.pokladna]` refuses every job — never enable it on a store before them.
- **Acks** are journaled and re-sent by the acker task until Odoo accepts them: transport error → stop the round + backoff; JSON-RPC / protocol error on ONE ack → keep only it owed, continue; a refusal (`not_found`, `not_claimed_by_you`, …) is final (`ack_note = "refused: …"`, ERROR log). `duplicate` = accepted. Every outcome wakes the acker (`Shared::ack_soon`) — the idle tick is only a safety net (the integration tests set it to 30 s on purpose so a missing wake-up fails them).
- **Logging**: job id / type / kasa / client_uuid / sale name / state changes; of the payload ONLY `amount` + `currency` (`DeviceJob::money`, its `Debug` prints payload KEYS only); never the api_key. Logging-only `if` branches become missed mutants — log one line with the value as a field (e.g. `recorded`, `reopened`), no arithmetic in log fields (`attempts + 1` was a missed mutant).
- **The `test` executor** (`test_executor = true`, E2E ONLY, never written by the installer) drives no device: a job needs `payload.devbridge_test.outcome` = `done` (+`delay_ms`) / `failed` / `indeterminate` / `crash`; anything else is refused "nothing ran". Its durable `test-device.db` is the device's memory reconcile reads. `crash` records the run and EXITS THE PROCESS (code 75) — tests inject a returning `CrashHook`.
- **E2E step 36** (`crates/devbridge-e2e/src/device_jobs.rs`): fake Odoo on pz-server TCP **9231** (the `DevBridge-E2E-FakeOdoo` firewall rule carries 9230 + 9231), `[client.pokladna]` on the RAW E2E client from the REAL installer functions (`wait_s` 10, asserted on every `next`) + `test_executor = true`. The forced restart is a real process death: the RAW task has a 1-minute keep-alive trigger (`-Once -RepetitionInterval 1 min`, `MultipleInstances IgnoreNew`, verified on pz-snv PS 5.1) — `e2e-cleanup.ps1` unregisters the task. The setup deletes `device-journal.db*` / `test-device.db*` of the E2E data dir each run (job ids are time-based too).
