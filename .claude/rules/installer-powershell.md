# Installer PowerShell — gotchas (auto-loads on installer/ and deploy/*.ps1)

- **Production runs Windows PowerShell 5.1 (as SYSTEM), not pwsh 7.** CI runs the installer Pester suite on BOTH (`installer-tests` job: pwsh 7 step + `shell: powershell` 5.1 step, #69). A test that passes only on pwsh 7 is a prod bug.
- **Never read a config with `Get-Content -Raw` and write it back as UTF-8.** PS 5.1 reads BOM-less UTF-8 as the ANSI code page, so the write-back double-encodes non-ASCII bytes. Use `[System.IO.File]::ReadAllText($Path)` + `WriteAllText($Path, $text, (New-Object System.Text.UTF8Encoding($false)))` (both serial-bridge merges do this since 0.8.36).
- **post-install.ps1 = procedural body; its helpers live in the sibling `installer/DevBridgeInstallerLib.ps1` (#80).** post-install dot-sources `Join-Path $PSScriptRoot 'DevBridgeInstallerLib.ps1'` and exits 1 BEFORE any change if it is missing. A NEW helper goes into the lib (functions ONLY — no top-level statements — pure ASCII, PS 5.1 syntax; `installer/tests/post-install-lib.Tests.ps1` asserts all three plus the exact function list, so add the name there too). The lib is shipped by listing it in `crates/devbridge-app/tauri.conf.json` `bundle.resources` right next to post-install.ps1 (both land in `<InstallDir>\_up_\_up_\installer\`); a new sibling file needs the same.
- **install.ps1 still can NOT dot-source anything** (it runs via `irm|iex` — no file on disk, `$PSScriptRoot` empty). A helper needed in both install.ps1 and post-install is defined inline in install.ps1 AND in the lib, and a Pester test asserts the two AST extents are byte-identical (`ConvertFrom-DevBridgeSerialBridgesSpec`). Edit one → copy verbatim to the other.
- **`post-install.ps1 -ValidateOnly`** loads the lib, runs only the read-only pre-change validation and prints `VALIDATE-OK <n> functions`, then exits 0 — the `e2e-deploy-client` packaging gate (`deploy/e2e-installer-packaging-gate.ps1`) runs the INSTALLED copy under 5.1 as SYSTEM on pz-snv and asserts the production `config.toml` hash is unchanged. Anything you add BEFORE the `-ValidateOnly` exit block must stay read-only.
- **Running a script as a real child process in Pester** (both editions): `Start-Process -FilePath (Get-Process -Id $PID).Path -ArgumentList "-NoProfile -ExecutionPolicy Bypass -File `"$script`" …" -Wait -PassThru -NoNewWindow -RedirectStandardOutput $o -RedirectStandardError $e` — same edition as the test run, no `2>&1` NativeCommandError surprises on 5.1 (see `post-install-lib.Tests.ps1`). Do not put `<word>` in an `It` name: Pester 5 treats it as a data-driven template placeholder and prints it empty.
- **Array `Should -Be`**: compare `(@($x) -join ",") | Should -BeExactly "a,b"` — a piped array unrolls and is not a reliable element-wise compare.
- **PowerShell hashtables are case-INSENSITIVE**; Rust `HashMap` keys (client_id) are case-sensitive. Use `[System.Collections.Hashtable]::new([System.StringComparer]::Ordinal)` when mirroring Rust key semantics.
- **Smoke a PS change under real 5.1 before pushing:** pz-server has only Pester 3.4, so do not run the suite there. Push the commit to the wip ref, then on pz-server `Invoke-WebRequest https://raw.githubusercontent.com/zbynekdrlik/devbridge/<sha>/installer/DevBridgeInstallerLib.ps1` (plus `post-install.ps1` into the SAME dir to smoke `-ValidateOnly -Mode server -DataDir <temp>`), AST-extract the functions (dot-source `deploy/lib/Get-FunctionSourceFromScript.ps1` from the same sha — the one extractor shared by both Pester suites and the E2E client setup, #70), and run them on a COPY of the live config in `C:\Windows\Temp\<dir>`. Delete the dir afterwards and confirm the live `config.toml` SHA256 is unchanged.
- The dev-branch CI E2E deploy replaces the binary on pz-snv and restarts the PRODUCTION `DevBridgeService` task too, so pjsnvs runs the dev build right after a green dev CI.
